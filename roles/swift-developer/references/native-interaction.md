# Choose a native interaction

Start with what the person is doing and where they expect to return. Use the app's existing presentation owner in either framework. The choice affects history, keyboard and accessibility focus, and what happens to an unfinished edit.

| User intent | Native shape | Check the return path |
| --- | --- | --- |
| Switch between peer destinations they use repeatedly | Use the app's tab structure. Preserve the relevant selection or navigation history in each destination. An item-specific action such as Add belongs inside its destination. | Navigate into one tab, switch away and back. Check the expected detail and selection. [Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars) |
| Inspect an item that belongs to a collection | Navigate within the current stack or select a detail in a split view. A stable item ID can express the same selection in compact and expanded windows. | Open the item, resize the window and return. Check the same item, meaningful back behavior and what happens if the item disappears. [Navigation and search](https://developer.apple.com/design/human-interface-guidelines/navigation-and-search) |
| Complete a bounded task, then return to the presenting screen | Consider a sheet for a new item or a multi-field edit. Decide whether edits are immediate or require Save, and give each dismissal path the same data contract. | Change a field, try the dismiss gesture, continue editing, cancel and save. Check the stored value and where focus returns. [Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets) · [Modality](https://developer.apple.com/design/human-interface-guidelines/modality) |

**Example — an offline grocery list.** One list with a detail screen needs no tab bar. An editor for an item's name can keep the original name and a working string locally. On Save, update that field on the current item through the existing store. A quantity changed elsewhere should survive the rename. Dismiss after the save succeeds and keep the draft available on failure. When the product promises to protect unsaved changes, let a clean draft dismiss immediately and give a dirty draft a way to keep editing or discard. For an autosaving editor, explain what Back means and verify the last edit survived.

When SwiftUI owns the flow, trace the binding or route that presents the editor. When a UIKit controller presents it, include presentation-controller delegate and gesture outcomes. Use the receiving view or window to determine available space. Test an edit while the keyboard is visible and, for a resizable target, keep the same selection as the window changes size. [Apple's UIKit sheet example](https://developer.apple.com/documentation/uikit/disabling-the-pull-down-gesture-for-a-sheet) · [Modernize your UIKit app](https://developer.apple.com/videos/play/wwdc2026/278/)
