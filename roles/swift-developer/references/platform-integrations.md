# Features that cross the app process

Determine which executable receives the event, which entitlement it needs and where state survives a process restart. Use the row matching the feature, then verify the relevant target's archive and runtime behavior.

| Symptom | Inspect and change | Evidence that addresses the failure |
| --- | --- | --- |
| A widget keeps showing yesterday's data | Follow the app's committed write to the shared container, then the extension's read and timeline. Check the App Group in the signatures for both products. Budgeted timeline reloads are scheduled by WidgetKit. | Update a known record and inspect the next supplied entry. Run the installed widget to check the displayed value and capture the time of the observed change. [App Groups](https://developer.apple.com/documentation/xcode/configuring-app-groups) · [WidgetKit updates](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date) |
| A payload fixture works but no update appears in production | Trace APNs environment, token and provider configuration separately from payload parsing. Background updates may be delayed, coalesced or dropped. Make a subsequent foreground refresh converge to the correct server state. | Exercise local payload handling, then attempt a delivery in the actual push environment if that is the claim. Record reception and completion. Keep tokens out of logs and reports. [Background notifications](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) |
| A paying customer loses access on a second device | Identify the product type. Reconstruct access for applicable products from verified current entitlements and process verified transaction updates. Deliver the purchased content or service before finishing the transaction. Treat replay idempotently. Consumable fulfillment needs its own durable accounting. | With a StoreKit configuration or sandbox account, cover pending approval, later completion, relaunch and revocation for the relevant product. Distinguish local simulation from store environment evidence. [Current entitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements) · [Transaction updates](https://developer.apple.com/documentation/storekit/transaction/updates) · [StoreKit Testing](https://developer.apple.com/documentation/xcode/setting-up-storekit-testing-in-xcode) |
| A background read of credentials fails only while the device is locked | Inspect the Keychain query, access group, accessibility class and returned status. Preserve the distinction between temporary unavailability and a missing item before writing a replacement or signing out. Choose the narrowest class compatible with the user-facing feature. | On an authorized test device exercise locked, unlocked and first-unlock conditions that matter to the feature. Verify the resulting account state without printing secrets. [Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility) |

For a new integration, follow the same evidence chain from the system event to the executable, signed capability, committed state and observable effect. Keep identifiers, logs and fixtures scoped to the test environment.
