# Investigating React frontend behavior

Start at the affected entry point. A monorepo may ship a browser SPA, two generations of Next.js routes and a component package with a wider React peer range. Read the owning package's manifest, workspace lockfile entry, relevant imports, router and build configuration. Check the resolved `react` and renderer versions together. For published components, also check the supported peer range. Record the facts that could change the decision, such as a server or client boundary, development Strict Mode, a production build, an enabled compiler or the target browser.

## Find the contract for this version

1. For a library, framework, SDK, API, CLI or service question, resolve its name in Context7 with the full question. Choose the authoritative match and a version-specific ID when available. Query that ID with the question and its relevant conditions. A supplied exact ID can go directly to the query. Routine code tracing, refactoring and business logic use local evidence.
2. Open the cited maintainer page. Check the version, router, runtime and whether the API is stable in the supported release. If Context7 is unavailable, omits the version or returns a conflicting excerpt, use the official docs, migration notes or reference at the installed release tag. Treat the bundled React, Tailwind and Vercel patterns as examples with their own assumptions.
3. When the documented behavior leaves a decision open, resolve the package from the consuming workspace. Inspect the selected export, type declaration or implementation at that version. For a framework regression, find an upstream test at the matching release or commit and compare its setup to the app. Record the file and symbol, release tag or commit. A test on the upstream default branch can suggest a reproduction for an older release.
4. When the outcome depends on runtime behavior, run the smallest interaction that distinguishes the candidate explanations. Record the route, initial state, command or browser action, build mode, expected result and actual observation. If the environment cannot run it, name the missing observation and the narrower conclusion the available evidence supports.

## Start with the observation that distinguishes the causes

| Report | First observation | Primary reference |
| --- | --- | --- |
| An editor loses its draft or shows the previous item's draft. | Type a marker, switch items and switch back. Trace the editor's parent position, component type and key across that transition. Establish which item should own the draft before changing its key. | [Preserving and resetting state](https://react.dev/learn/preserving-and-resetting-state) |
| A route warns during hydration or visibly changes as it loads. | Hard-load the route and compare the document response with the first client render at the first mismatch. Check locale, clock, browser storage and server-provided values. Test client navigation separately. | [Hydrating server-rendered HTML](https://react.dev/reference/react-dom/client/hydrateRoot) |
| A successful write leaves an App Router view stale. | Identify who reads the value in this segment. Compare the mutation response, the next server read and the visible client state. Inspect the fetch options and invalidation call in their actual server context. An upgrade may change caching defaults. | [App Router revalidatePath](https://nextjs.org/docs/app/api-reference/functions/revalidatePath) · [Next.js 15 upgrade notes at v15.1.11](https://github.com/vercel/next.js/blob/v15.1.11/docs/01-app/02-building-your-application/11-upgrading/03-version-15.mdx) |
| A Pages Router page shows old props after navigation. | Inspect the page's exported data function. Compare a direct request and client-side navigation, noting which requests ran, their props and any client cache retaining earlier data. | [Pages Router getServerSideProps](https://nextjs.org/docs/pages/building-your-application/data-fetching/get-server-side-props) |
| TanStack Query shows another filter's results or a rollback restores the wrong list. | Compare the full query key used by the reader, the key updated by the writer and the prefix invalidated on settle. Include each input that changes the returned data. Observe two different filters. | [Query keys at v5.90.3](https://github.com/TanStack/query/blob/v5.90.3/docs/framework/react/guides/query-keys.md) · [Mutation callbacks at the same release](https://github.com/TanStack/query/blob/v5.90.3/docs/framework/react/reference/useMutation.md) |
| A dialog loses focus when dismissed or focus escapes behind it. | Open it by keyboard, follow Tab and Shift+Tab, dismiss it and identify the element receiving focus. Inspect the accessible name and focus target in the target browser. | [WAI-ARIA modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) |
| An interaction feels slow. | Reproduce it with the same input and build conditions. Inspect a browser trace for request, script, layout or paint time. If React work dominates, profile the affected subtree and compare commits before and after the change. | [Chrome Performance panel](https://developer.chrome.com/docs/devtools/performance/reference) · [React Profiler](https://react.dev/reference/react/Profiler) |

For example, a query subscriber using `['tickets', { page: 1, open: true }]` sees old results. At v5.90.3, `QueryCache.build` selects a cache entry by hash. Its default `hashKey` sorts the keys of plain objects. In the app's QueryClient, write a marker under this key, then read it with the two properties in reverse order. With default hashing the marker should be present. Change the page to 2 and the read should miss. If the first read misses, check for another client instance or a custom hash before adding memoization. [Cache lookup](https://github.com/TanStack/query/blob/v5.90.3/packages/query-core/src/queryCache.ts) · [Hash implementation](https://github.com/TanStack/query/blob/v5.90.3/packages/query-core/src/utils.ts)

Report the scoped finding with the project path, official page or pinned source, and the observation that supports it. Distinguish a documented guarantee from an observed implementation detail or an inference. Stop when the remaining uncertainty would leave the chosen change and its acceptance check the same.
