# Evaluation and decision review

These are behavioral specifications, not recorded model results:
64 cases in 7 target groups and 6 multi-turn scenarios. They cover scope,
authorization, affected-scope tests, defect repairs, explicit outcomes and Graph v3
ownership. Test cases cover regression reproduction, meaningful assertions, real
integration paths, isolated fixtures, zero-selected tests, check reuse, justified
scope expansion, required broad gates and honest failure reporting.

## Automated evidence

`scripts/tests/emperor-rolebox.test.ts` uses the sibling rolebox loader/resolver,
strict v3 compiler, host-bound tools and real SQLite acceptance store with scripted
dispatch. It checks these contracts:

- Every department resolves with local skills and executable tools; Test resolves
  test-design and no Validator dispatch target remains.
- All topology templates compile; old grammar and retry fields are rejected.
- Accepted done routes once and carries pinned declared inputs; replay is idempotent.
- Assigned Test work waits for implementation reports and settles through normal
  execution outcomes, preserving failed regression reports without a judge stage.
- Non-success outcomes do not release done-only consumers.
- Approval preparation is context, while host approval requires its authorized
  session and does not submit a result.
- Workers cannot declare, query or control graphs.
- Execution-budget rejection does not commit an accepted result or successor.
- Function continuation requires an accepted response, not signals, fences or calls.

Python mutation tests detect tree, permission, activation, completion-gate,
shared-copy drift and removed/unknown agents in graph examples and eval targets.
These checks make no model calls. They do not establish how well a live model writes
tests, chooses scope or follows instructions.

Topology templates do not install schemas or trusted command validators for business
reports. Consumers still check prerequisite completeness; structured acceptance alone
does not establish that reported checks succeeded. Actual check results belong in
Execution Reports rather than a separate independent verdict.

## Behavioral comparison (not run)

Use identical disposable fixtures, host/model configuration and budgets for baseline
and candidate runs. Confirm intended roles and skills loaded for each target. Start
with local-fix-selects-relevant-tests, regression-fails-for-the-right-reason,
meaningful-assertions, zero-selected-is-not-pass, broaden-for-shared-config and
reuse-unaffected-results. Preserve prompts, accepted reports, actual test commands,
selected tests, workspace diffs and check output; never retain worker credentials.

Measure defect detection on seeded faults, new regression coverage, unnecessary
full-suite runs, repeated current checks, scope violations, false pass reports,
repair count, dispatch count, wall time and tokens. Include cases requiring broader
checks so reduced test execution cannot hide regressions. Pair and repeat runs to
separate model variance from actual improvement. Distinguish deterministic
configuration/transport checks from live behavioral evidence.
